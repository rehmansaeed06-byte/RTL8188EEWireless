## SEVENTEENTH UPDATE (read this first) — 5 more kextutil/kmutil load
## symbols closed (udelay/mdelay/usleep_range wiring gap, fls,
## get_random_bytes). 48 → 36 undefined symbols total across this
## and the SIXTEENTH UPDATE. Kext still does not load.

Same session as the SIXTEENTH UPDATE below, continued. Picked off
the easiest remaining symbols per that update's own "likely fastest
next win" note. Full detail: `docs/findings.md` Section 89.

**Two genuinely different root causes, not one** — worth remembering
for whatever's tackled next:

1. `udelay`/`mdelay`/`usleep_range` — `compat/linux/delay.h` already
   had real, correct implementations. Just never `#include`d from
   anywhere reachable (confirmed: only `iopoll.h` referenced it, and
   nothing includes `iopoll.h` either). Went undetected as a compile
   error only because `DRIVER_CFLAGS` carries
   `-Wno-implicit-function-declaration` — this flag is worth
   suspecting behind any future "clean build, kext still won't load"
   symbol. Fixed by wiring `delay.h` into `rtlwifi_compat.h`'s
   force-included umbrella, same pattern as the existing
   `linux/time.h`/`linux/atomic.h`/`linux/interrupt.h` includes
   there.

2. `fls` — a genuinely different, more subtle case. MacKernelSDK's
   `<libkern/libkern.h>` really does declare `extern int
   fls(unsigned int);`, and that declaration really is reachable in
   driver translation units (confirmed the hard way: a first-attempt
   `static inline fls()` redefinition failed to *compile* with
   "static declaration follows non-static declaration" — proving the
   real declaration was in scope). But the shipped kernel apparently
   doesn't actually export a symbol named `_fls` under that KPI
   despite the header claiming it — confirmed via `kextutil -t`.
   **A header declaring something doesn't mean it's actually
   exported for third-party kexts to link against** — don't trust
   header presence alone as proof a symbol will bind. Fixed by
   defining a differently-named function (`rtlwifi_fls`) and
   redirecting real call sites via `#define fls(x) rtlwifi_fls(x)`,
   since redefining `fls()` itself would re-collide with the real
   declaration.

`get_random_bytes` was genuinely new (no implementation existed
anywhere), modeled on `RTW88IEEE80211.cpp`'s already-working direct
call to MacKernelSDK's `read_random()` — hit one more real,
independent bug along the way: `<sys/random.h>` uses the BSD `u_int`
typedef in its own declaration without pulling in the header that
defines it, so the real rtlwifi driver `.c` files (compiled with
`-D__KERNEL__`, unlike `RTW88IEEE80211.cpp`) don't have `u_int` in
scope. Fixed by defining it locally, guarded with the SDK's own
`_U_INT` macro so it's harmless if the real header shows up too.

**Net: 41 → 36 undefined symbols**, confirmed via 3 separate clean
`rm -rf build && make` runs plus `kextutil -t` re-checks, zero
regressions each time. Kext still doesn't load — 13 kernel-primitive
symbols left (`_local_irq_*`, `_rcu_read_*`, `_be16_to_cpup`,
`_ether_addr_equal_*`, `_timer_delete_sync`, `___skb_dequeue`,
`___skb_queue_purge`, `_skb_queue_is_last`, `_dev_warn`,
`_pci_resource_flags`, `_pcie_capability_clear_and_set_word`), ~21
mac80211 API stubs untouched, plus the still-standalone
`_rtl88ee_hal_cfg` and still-deprioritized `_thread_call_cancel_wait`.

**Process note for next session:** given this round found two
different root causes behind symbols that looked identical from
`kextutil -t`'s flat symbol list, check each remaining symbol in two
steps before writing anything: (1) grep for whether a correct
implementation already exists somewhere unreached in
`src/compat/` (like `delay.h` was), and only if genuinely absent,
(2) check whether a plausible MacKernelSDK/libkern equivalent exists
— and if so, whether relying on it directly actually compiles
without a redeclaration conflict, not just whether the header
declares it (like `fls` needed).

The FIFTEENTH UPDATE below got a full clean build for the first

**48 unique undefined symbols at load time** (deduped with
`grep -o "bind ([^)]*)" | sort -u` — raw kmutil output repeats each
one per call site, thousands of lines). Ruled out a KPI-version
mismatch first (`Info.plist`'s `20.0.0` vs the real kernel's
`21.6.0` — forward-compatible, confirmed via `kextstat`) before
categorizing the 48 into: real bugs in our own code (8, all fixed
this session), genuinely-missing kernel-runtime primitives (~15,
`_udelay`/`_mdelay`/`_rcu_read_lock`/etc. — still open), missing
mac80211 API stubs (~25, `_ieee80211_find_sta`/`_ieee80211_beacon_get`/
etc. — still open), and one standalone gap, `_rtl88ee_hal_cfg` (not
yet root-caused, confirmed independent of the fixes below since it's
still unresolved after them).

**The real bug, architecturally the most important one:**
`RTW88IEEE80211.cpp` (reused from Feixiao) was still calling
`rtw_pci_probe`/`rtw_pci_remove` — real rtw88 upstream entry points,
`struct rtw_dev *`-based — despite this project compiling rtlwifi,
not rtw88. Everything *downstream* of the probe call in the same
file was already correctly ported to rtlwifi's names
(`rtlwifi_get_hw()`, `rtlwifi_register_vif()`, `struct rtl_priv *`)
— only the declarations block and 2 call sites were stale. Fixed by
switching to the real rtlwifi entry points, confirmed via direct
source read: `int rtl_pci_probe(struct pci_dev *, const struct
pci_device_id *)` / `void rtl_pci_disconnect(struct pci_dev *)` —
note the real teardown function's name matches the `pci_driver
.remove` field, not a `*_remove` suffix.

**6 more real bugs, same root cause (files reused verbatim from
Feixiao, never fully adapted):** `rtw88_printk`/`rtw88_log_level`/
`rtw88_module_start`/`rtw88_module_stop`/`rtw88_read_log`/
`rtw88_trigger_interrupt` were declared in `kernel.h`/
`RTW88UserClient.cpp`/`kmod_info.c` but never defined anywhere in
this tree. Implemented for real in `rtlwifi_compat.c` — not stubs,
since `pr_err`/`WARN`/etc. all expand to `rtw88_printk()` and are
called throughout the real, compiled-in rtlwifi source. Ring-buffer
+ `IOLog()` mirror for the logging pair; `rtw88_module_start/stop`
are the kext's real kernel-called entry points
(`KMOD_EXPLICIT_DECL`), bodies deliberately minimal since real
bring-up happens later via IOKit's own probe/start(), not at
kmod-entry time; `rtw88_trigger_interrupt` left an explicit no-op
(same confirmed-no-op-over-guessed-behavior precedent as prior
sessions' `compat_init`/`_exit`) since no real MMIO trigger register
is documented anywhere and guessing risks writing to an undefined
register on real hardware.

**Two gotchas hit and fixed along the way, both worth remembering:**
(1) a comment containing the literal text `rtw_core_*/rtw_tx` closed
the C block comment early at the `*/`, turning the rest into real
(broken) code — same `-Wcomment` class already flagged elsewhere in
this project, but here it wasn't just a warning. (2) The first
logging implementation used `IOSimpleLockLockDisableInterrupt`/
`UnlockEnableInterrupt`, which don't bind at load time despite being
declared in `iokit_shim.h` (showed up as 2 new undefined symbols,
turning a clean -8 into a net -6). Fixed by matching this project's
own already-proven pattern (`RTW88PCIDevice.cpp`'s `_dmaLock`, used
directly from `handleInterrupt()` — plain `IOSimpleLockLock`/`Unlock`,
safe because `IOInterruptEventSource`'s callback runs on the
IOWorkLoop thread, not true primary-interrupt context).

**Net result: 48 → 41 undefined symbols.** Confirmed via 3 separate
clean `rm -rf build && make` runs across this session (once after
the probe/remove fix, once after the logging functions were first
added, once after the IOSimpleLock correction) — all three fully
clean, zero `error:` lines, only the same pre-existing warning-level
noise as the FIFTEENTH UPDATE's build. **The kext still cannot
load** — this session closed naming/wiring bugs in our own code, not
the missing compat-shim coverage, which is most of what's left.

**A much bigger, previously-undetected bug found while fixing the new
code, affecting 3 already-shipped files:** adding the new TX-ring
bridge functions needed real rtlwifi's `pci.h` (for `rtl8192_tx_ring`/
`BE_QUEUE`/`rtl_pcidev()`), and a first attempt to `#include "pci.h"`
produced "incomplete type" errors — not a missing include, a
*shadowed* one. `Makefile.rtl8188ee`'s `DRIVER_CFLAGS` had this port's
own compat-shim `-I` paths listed BEFORE the real-rtlwifi `-I` paths,
so quote-form `#include "pci.h"` was silently resolving to this port's
own unrelated IOKit-facing `pci.h` (same filename, completely
different header) instead of real rtlwifi's. Live grep against real
rtlwifi source found `base.c`, `efuse.c`, and `pci.c` itself all do
this same `#include "pci.h"` — and all three are already in
`DRIVER_SRCS`, already compiled into every prior build of this
project. **All three have been silently compiling against the wrong
header this entire project**, not just for this session's new code —
a real bug in already-shipped source, only surfaced because new code
happened to need a symbol the wrong header didn't have. Fixed by
reordering `DRIVER_CFLAGS` so real rtlwifi's headers win. Confirmed
safe to reorder (not just convenient) by cross-checking every real
rtlwifi header filename against every compat-shim header filename
first — only `pci.h` and `usb.h` collide, and `usb.h`'s only real
consumer (`usb.c`) isn't in this port's build at all.

**Real compile confirmation, in two stages** (`docs/findings.md`

With both `RTW88IEEE80211.cpp` and `RTW88PCIDevice.cpp` now

## MAJOR CORRECTION (read this first)

## Core architectural conclusion
RTL8188EE belongs to Linux's older `rtlwifi` family, not `rtw88`.
The port therefore needs rtlwifi's shared core plus RTL8188EE-specific code, wrapped by Feixiao's macOS/IOKit layer.

The architecture, CONFIRMED by direct source/Makefile audit (findings.md
Section 45), is:

Feixiao macOS/IOKit wrapper (RTW88PCIDevice.cpp, RTW88IEEE80211.cpp —
    drives the compiled-in rtw88 core via its real entry points)
  -> src/compat/rtw88_compat.c (Linux-primitive shim implementations,
       PLUS a small number of genuinely OS-specific bridge functions
       that cast hw->priv directly to struct rtw_dev *)
  -> src/compat/linux/*.h, src/compat/net/mac80211.h (LinuxKPI-style
       header shims — intercept every linux/*.h and net/*.h #include)
  -> REAL, UNMODIFIED rtw88-stable/.../rtw88/*.c (main.c, mac.c, phy.c,
       fw.c, tx.c, rx.c, pci.c, all chip-specific *.c — compiled AS-IS,
       not hand-translated, per Makefile DRIVER_SRCS/CHIP_SRCS)
  -> firmware (embedded as compiled-in blobs, NOT loaded via any
       macOS equivalent of request_firmware_nowait — see below)
  -> hardware

The equivalent architecture for RTL8188EE is expected to be: a new/
extended compat layer + real unmodified rtlwifi/rtl8188ee source files
+ a new small rtlwifi_compat.c + a new/generalized IOKit driving layer
+ embedded rtl8188efw.bin blob. NOT a rewrite of rtlwifi's own C files.

## Confirmed PCI architecture
rtlwifi has shared `rtl_pci_probe()`.
RTL8188EE's `sw.c` uses `.probe = rtl_pci_probe`.

This mirrors the broad rtw88 design:
PCI driver -> shared PCI probe -> chip-specific configuration/operations.

But the structures differ:
- rtw88: `rtw_chip_info`, `rtw_dev`
- rtlwifi: `rtl_hal_cfg`, `rtl_hal_ops`, `rtl_priv`, `rtl_hal`

## Confirmed private-data model
`rtl_pci_probe()` allocates `ieee80211_hw` with space for `rtl_pci_priv + rtl_priv`.
`hw->priv` is a `struct rtl_priv *` accessed through rtlwifi's `rtl_priv(hw)` mechanism.
The rtl_priv object has a flexible private tail associated with PCI state.

Therefore the Feixiao cast from rtw88's `hw->priv` to `struct rtw_dev *` must become the rtlwifi equivalent.

## Feixiao wrapper analysis
`Feixiao/src/kext/RTW88IEEE80211.cpp` has a relatively small direct rtw88 footprint.

Current rtw88 PCI table contains:
- 0xB822 RTL8822BE
- 0xC822 RTL8822CE
- 0xC82F RTL8822CE variant
- 0xC821 RTL8821CE
- 0xB821 RTL8821CE variant
- 0x8821 RTL8821AE
- 0x8812 RTL8812AE
- 0x8813 RTL8814AE

RTL8188EE 0x8179 is absent.

Important finding: for a single RTL8188EE target, a multi-chip rtw88-style lookup table is probably unnecessary. The rtlwifi `rtl88ee_hal_cfg` can be used directly.

The expected mechanical conversion is roughly:
- `struct rtw_chip_info *` -> `struct rtl_hal_cfg *`
- `rtw_pci_probe()` -> `rtl_pci_probe()`
- `struct rtw_dev *` -> `struct rtl_priv *`

Generic macOS/802.11 wrapper logic is much more reusable.

## Important channel-switch / LPS finding
RTL8188EE channel switching was inspected in:
`linux-kernel/drivers/net/wireless/realtek/rtlwifi/rtl8188ee/phy.c`

Functions inspected:
- `rtl88e_phy_sw_chnl_callback()`
- `rtl88e_phy_sw_chnl()`
- `_rtl88e_phy_sw_chnl_step_by_step()`

There is a `do { ... } while (true)` loop, but it is a scripted step-by-step state machine, not an indefinite register-polling loop.

The inspected path uses bounded `mdelay(delay)` calls and predefined channel-switch commands. No pattern like `while (read_reg(...) & BIT_X)` waiting indefinitely for hardware/firmware was found.

### Consequence
The specific rtw88 LPS hazard that motivated a custom connection/channel bridge was NOT found in the inspected RTL8188EE rtlwifi channel-switch path.

Therefore the current preferred design is to use normal rtlwifi/mac80211 channel operations rather than inventing an RTL8188EE-specific channel-switch bypass.

This is a strong static-analysis conclusion, not runtime proof.

Still open: verify whether RF calibration/IQK is automatically handled appropriately after channel changes.

## Confirmed TX path
Full chain traced source-to-source (findings.md Section 40.7):

```
mac80211 -> rtl_op_tx (core.c) [gate checks: RF power on, interface started]
  -> intf_ops->waitq_insert (rtl_pci_tx_chk_waitq_insert)
  -> intf_ops->adapter_tx = rtl_pci_tx (pci.c)
       [lock, select ring/desc by hw_queue, ring-full check via
        cfg->ops->get_desc(HW_DESC_OWN)]
       -> cfg->ops->fill_tx_desc = rtl88ee_tx_fill_desc (trx.c)
       -> cfg->ops->set_desc(HW_DESC_OWN) [hand off to hw]
       [unlock, backpressure if <2 free descriptors]
       -> cfg->ops->tx_polling = rtl88ee_tx_polling (trx.c) [hw kick]
```

Two separate ops tables involved: `intf_ops` (bus/transport,
PCI-specific — this is the layer needing a full IOKit/PCIe rewrite)
vs `cfg->ops` (chip behavior — same dispatch pattern as hw_init,
dm_watchdog, switch_channel, etc.). Chip-specific fill/polling
functions are comparatively narrow and self-contained.

Open sub-item: which `use_new_trx_flow` branch RTL8188EE uses —
**RESOLVED (findings.md Section 40.9.2): `use_new_trx_flow = false`**
for RTL8188EE (only RTL8192EE/RTL8822BE use the newer flow) — older
`ring->idx`-based indexing applies.

## Confirmed PCI BAR mapping / MMIO register access
Full chain traced (findings.md Section 40.8):

- `_rtl_pci_io_handler_init` (pci.c:344) — trivial, just wires
  `rtlpriv->io.read*/write*` function pointers to `pci_*_sync/async`
  primitives (pci.h:243-273).
- Those primitives are plain `readb/readw/readl` /
  `writeb/writew/writel` over `rtlpriv->io.pci_mem_start + addr`.
  "sync"/"async" is standard Linux MMIO terminology (posted write vs
  blocking read), not threading/queuing — no locking involved.
- `pci_mem_start` is set inside `rtl_pci_probe` itself:
  `pci_request_regions` → `pci_resource_start/len/flags(pdev,
  rtlpriv->cfg->bar_id)` [bar_id is chip-specific, from rtlpriv->cfg]
  → `pci_iomap(pdev, bar_id, pmem_len)` → `pci_mem_start`. Plus two
  PCI config-space writes (not MMIO): disable Clock Request (0x81),
  leave D3 (0x44).
- Teardown: `pci_iounmap`.

Low-risk macOS translation target: maps cleanly onto
`IOPCIDevice::open()` + `mapDeviceMemoryWithIndex` (BAR mapping) and
`IOMemoryMap`'s `readRegister*`/`writeRegister*` (register access).
The two config-space writes go through a different macOS API
(`configWrite8`), not the BAR-mapped accessors — worth keeping
separate in the eventual port.

Still unread: `rtl_pci_parse_configuration` (called at the end of
`_rtl_pci_find_adapter`, presumed ASPM/link-control parsing) and
`rtl_pci_intr_mode_msi`/`_rtl_pci_interrupt` (MSI IRQ registration,
directly Tier-1 relevant — new lead, not yet read).

`_rtl_pci_find_adapter` (pci.c:1798) is now fully read (findings.md
Section 40.9): PCI device-ID → `rtlhal->hw_type` dispatch table
(confirms `RTL_PCI_8188EE_DID` → `HARDWARE_TYPE_RTL8188EE`), sets
`use_new_trx_flow` (see TX path section above), and does PCI-bridge
vendor/ASPM-quirk detection. No hazards found. **Both originally-

## Bottom line
The project is NOT simply "port the whole Linux driver" — and, per the
Section 45 correction above, it is also NOT "hand-translate rtlwifi's C
into new IOKit-native code." It is: compile real, unmodified rtlwifi
source against an extended Linux-compat shim layer, the same strategy
Feixiao already uses for rtw88.

The evidence currently says:
1. RTL8188EE uses rtlwifi, not rtw88.
2. rtlwifi has a shared PCI probe analogous to rtw88.
3. RTL8188EE has `rtl_hal_cfg` + `rtl_hal_ops` for chip-specific behavior.
4. `hw->priv` is `rtl_priv`.
5. **CONFIRMED (was previously an estimate): Feixiao's macOS wrapper
   does not reimplement rtw88's driver logic at all — it compiles real
   upstream rtw88 source directly and has only a thin, genuinely
   OS-specific bridge/compat layer.** This is a stronger and different
   claim than "relatively small direct rtw88 dependency."
6. A dedicated rtw88-style PCI-ID table is unnecessary for the single RTL8188EE target.
7. The suspected rtw88 LPS/channel-switch hazard was not found in the inspected RTL8188EE channel-switch path.
8. Normal rtlwifi/mac80211 channel operations are therefore preferred unless later source/runtime evidence shows otherwise.
9. RF calibration (IQK) on RTL8188EE is driven by hw_init (once) and a periodic thermal-drift watchdog — never by channel switch — so rtw88_connect_hw_setup's forced-calibration step also has no needed rtlwifi equivalent. Both reasons for that bridge function's existence are now accounted for by rtlwifi's normal paths (static analysis; runtime boot test still pending).
10. The main remaining challenge is now **compat-layer Linux-API coverage** (does the existing rtw88-targeted shim cover what real rtlwifi source needs, and where must it be extended) rather than hand-translating PCI/DMA/IRQ/MMIO logic into IOKit.

This knowledge is what's needed to write a correct, minimal `rtlwifi_compat.c` — it does not mean rtlwifi's C files need hand-porting; they don't, per Section 45.
